BASE

把个人提效，

01 / 从实际工作出发

个人快了，组织没快。

这是我在实际工作中的核心判断：员工已经通过很多 AI 工具提升了个人效率，但组织整体并没有随之提高。

公司里并不缺少使用 AI 的方式。有人用办公助手处理日常事务，有人用工作流完成重复任务，也有人借助开发工具搭建自己的 Agent。个人可以更快地产出一份分析、一版原型或一段代码，但这些改善没有自然汇集成组织的整体提升。

岗位内部

每个人做自己的事更快了

资料检索、内容生成、设计开发、重复操作，都有了新的提效工具。

岗位之间

工作仍靠人反复连接

上下文要重新解释，成果要重新整理，判断标准要重新对齐，相似能力仍被重复搭建。

01

经验没有进入工作过程

好方法散在个人经验、聊天和文档里。拿到材料之后，其他人仍未必知道什么时候用、怎样用，以及哪些情况不适用。

02

交付缺少共同标准

AI 可以更快生成内容，但什么算做好、下游能否接着用，仍需要反复解释、判断和对齐。

03

这次纠错没有改善下次

人把当前结果修好了，修改原因却没有进入方法和规则，同样的问题下一次仍会出现。

我因此把关注点从“怎样让更多人用上 AI”，转向“怎样让一个人的提效，能够被上下游接住，并持续沉淀下来”。组织提效需要同时处理协作中的信息损耗、重复建设和经验传承。

BASE 首先要回答的问题

怎样让经验能够复用、交付能够验收、纠错能够积累，进而形成组织共同使用和持续维护的工作系统？这也是模板、岗位自定义与项目空间设计的出发点。

02 / 核心价值

四项价值，以组织提效为中心

01 / 核心价值

组织提效：让个人成果成为上下游可继续使用的输入

把岗位 Context、工作方法、交付物与任务状态放到共同的工作空间里，让不同角色围绕同一业务目标和验收标准协作。前一环节的产出能够被下一环节采用，成熟方法能够复用，减少重复搭建、等待、反复对齐和返工。

关注的变化：从“每个人更快完成自己的部分”，走向“整个团队更顺畅地完成一件事”。

02 / 企业稳定性

岗位稳定：人员变化后，工作仍能延续

同一个岗位换人接手，前人的材料、判断经验和工作习惯往往没有完整留下。新人需要重新摸索，产出也容易随个人经验出现波动。

BASE 希望把这些积累组织进岗位 Agent：业务背景、历史案例、常用模板、工具、工作流程，以及什么算“做好”的判断标准。新员工接手的是一套可以继续使用和完善的工作基础。

上手阶段

更快找到岗位资料，理解工作方法，沿着已有范例完成任务。

长期使用

在历史经验与持续更新的规则支持下工作，减少反复试错，提高长期效率与产出稳定性。

要沉淀的不是某个人的全部判断，而是可维护的方法、依据与经验。负责人仍需要校准规则，让岗位资产跟随业务变化。

03 / 企业管理

让 AI 投入可见、可管、可判断

企业需要知道哪些 Agent 在服务什么业务、消耗多少资源、效果如何，也需要明确谁定标准、谁改规则、谁批准发布。把资产归属、权限、版本和维护责任一起管理，才能让 AI 投入与业务收益建立联系。

关注的变化：从分散的个人账号与配置，走向有责任、有边界的组织资产。

04 / 员工个人提效

从现成能力开始，按岗位需要调整

员工既可以直接使用适合自己的 Agent 模板，也可以补充业务资料、调整工作方式。不必人人从零搭建，就能更快完成日常分析、写作、检索、设计和重复任务。

关注的变化：降低使用与建设门槛，让已有能力真正进入每天的工作。

四项价值是相互支撑的：个人用得顺，能力才会被持续使用；经验能沉淀，岗位才更稳定；资产可管理，复用才有边界；不同岗位连接起来，才有机会形成组织提效。

03 / 从价值到产品

把岗位能力，连接成可以交付和改进的工作系统

沿着“个人快了，组织没快”的判断，我的思考从共享单个 Skill，走到可复用的岗位工作基础，再走到能够交付和持续改进的业务闭环。

01

共享经验，要连同适用条件与交付标准

一段方法要持续有效，还需要业务资料、历史范例、工具和质量要求。模板因此要说明：解决哪类任务、在什么条件下使用、怎样推进、什么算做好，以及已知限制。

02

岗位是使用入口，业务任务是协作与验收的基本单位

“产品经理 Agent”帮助员工找到入口；真正需要定义清楚的是“澄清一条需求”“完成一次竞品监测”等任务。同一个人可以使用不同能力，一个任务也可能跨越多个岗位。项目空间据此连接输入、交付版本、验收人和下一步。

03

把工作完成，也让下一次工作有所改善

模板承载共性，自定义适配业务差异，项目空间承接协作。它们还需要连接两个闭环：本次任务能交付，执行中的问题能够反过来改善共享能力。

闭环 01 / 任务交付

让这一次工作可以交付

  1. 明确目标与标准
  2. Agent 执行
  3. 检查实际结果
  4. 人工确认或退回
  5. 下游继续使用

明确标准的重复步骤可以自动检查；价值取舍、关键验收和有外部影响的动作保留人工判断。

闭环 02 / 能力改进

让下一次少踩同样的坑

  1. 记录修改与退回
  2. 分析问题原因
  3. 提出方法或规则修改
  4. 用案例验证
  5. 负责人批准并发布

一次修改可能是个人偏好、特殊情境或资料不足。先判断原因，再决定是否进入共享模板，不能把所有用户修改直接当作新规则。

设计示例 / 非已上线流程

从一条模糊需求，到下一次更可靠的交付

  1. 澄清：业务方提交一句需求，Agent 根据历史案例与岗位规范补齐关键问题。
  2. 定标：PM 确认目标、范围和验收标准，形成后续可引用的需求版本。
  3. 交付：生成 PRD 与原型，检查字段、状态和交互是否一致。
  4. 纠错：评审发现异常状态缺失，记录退回原因与修正内容，再次检查后交接。
  5. 改进：维护者判断是否为共性问题；必要时补充规则，用历史案例验证，批准后发布模板新版本。

这条产研链用于解释产品机制。模板和岗位工作台面向企业不同业务场景，推广顺序应由真实需求决定。

共享模板保留通用方法，岗位实例承载业务差异。团队私有资料、访问权限与个人修改分别管理；可共享的经验经过验证后再进入组织资产。

04 / 竞品分析后的判断

现成工具提供能力，BASE 组织岗位的使用方式

从 WorkBuddy、千问办公、豆包工作以及 Dify 等产品中，我看到专家角色、技能复用、企业上下文、自动化与人工审核已经在发展。BASE 的重点因此落在：如何围绕企业岗位，把这些能力组织成可使用、可维护、可协作的工作方式。

参照方案值得借鉴的部分对 BASE 的启发
WorkBuddy专家与专家团，把专业角色和协作方式变成可调用的能力。用模板降低上手门槛，同时让具体岗位能够调整资料、方法与交付要求。
千问办公结合办公生态，提供技能、连接器、定时任务和企业管理入口。把日常任务与自动运行结合起来，让管理与使用处于同一体系。
豆包工作结合企业知识与用户权限，成果可回到协作平台继续使用。岗位 Agent 要能接住组织已有的上下文，并把新成果继续沉淀回去。
Dify流程编排与人工输入节点，可将审核和分支纳入执行过程。确定步骤可以交给工作流；业务用户仍需要适合岗位任务的交互入口。

我更关注组合后的实际价值：员工是否容易使用，岗位是否能持续维护，成果是否能被上下游复用。现有平台能承接的能力可以接入，BASE 集中处理岗位配置、资产关系和协作体验。

05 / 三个设计亮点

可复用、可定制，也能一起工作

原型围绕三个重点展开：让能力能够复用，让工作方式可以定制，让不同岗位能够围绕项目协作。完整交互可以进入 Demo 查看。

亮点 01 / 模板与自定义

一个人搭好模板，其他岗位从已有积累开始

建设者先把专业方法、工具和默认工作区沉淀为 Agent 模板。使用者找到适合自己的模板后，可以按现有配置直接使用，也可以创建适合本岗位的版本，补充资料、调整报告形式与能力组件。

直接使用

选择适合任务的模板 → 接入必要资料与授权 → 开始工作。

基于模板定制

保留通用骨架 → 调整岗位配置 → 预览、试用并保存自己的实例。

设计重点：把“使用”与“建设”分开，让员工不必先理解所有底层配置，也能开始完成工作。

设计延伸 · 待实现

模板需要继续承载什么

除默认组件和工具外，还应明确适用任务、输入要求、方法与示例、交付标准、已知限制和维护者，让经验真正进入使用过程。

亮点 02 / 可配置的工作方式

自定义覆盖 Context，也覆盖 Agent 怎样工作

Context Engineering 为 Agent 提供业务依据。岗位差异还包括需要哪些工具、如何触发和执行，以及怎样与人交互。BASE 希望把这些差异落实为可预览的组件与配置；DeepSeek Harness 是当前探索的运行接入选项。

可定制方向岗位使用者或建设者可以改变什么
Context 与岗位规范业务资料、规则、历史范例、Skill、输出结构和验收要求。
工具与数据能力选择检索、文件处理、数据采集或业务连接器，并配置可访问的范围。
模型与执行方式按任务选择模型和能力组合；需要时在单任务内部增加分工与检查步骤。
触发与交互手动发起、定时运行或事件触发；对话、表格、画布与审核队列配合任务使用。
历史与反馈决定保留哪些任务记录、引用哪些历史产物，以及如何收集修改和退回原因。

设计重点：配置先生成可预览的草稿，试用后保存；涉及共享规则、工具权限与新增代码的变化，需要对应负责人确认。

设计延伸 · 待实现

自定义的边界

员工可以调整任务资料、输出形式和工作方式；共享质量标准、权限和关键规则的变更，交给对应负责人维护与批准。

亮点 03 / 项目空间

让岗位之间的工作，围绕同一份项目资产延续

项目空间把目标、任务、资料、交付物和人工节点放在一起。不同角色进入自己的岗位工作台，也能理解上游产出了什么、当前轮到谁处理、下游需要什么。

例如，需求洞察整理出的需求与验收标准，可以成为原型设计的输入；设计方案与约束继续进入研发任务。关键是约定输入输出、保留交付版本和确认人，而不只是把多个 Agent 画在一张图上。

设计重点：工作在岗位间流转，依据与决策也随之保留；项目成员能够在已有成果上继续推进。

设计延伸 · 待实现

06 / 技术取舍

复用执行底座，把建设重点放在业务机制上

通用执行能力优先复用成熟框架和服务。BASE 重点建设业务上下文、交付标准、责任关系与反馈机制，并保留替换底层运行方案的空间。

我把这部分业务工作基础理解为 Business Harness：让企业经验与标准进入执行、验收和持续改进的机制。它包含产品设计和组织分工，需要业务团队共同建设。

AGENT 运行层接入可替换的执行能力

模型、工具、上下文装配、执行与会话记录。DeepSeek Harness 是当前探索选项。

一份交付物，需要能够回答

用了什么资料、哪个规则版本，执行了哪些关键操作，谁确认过，为什么被退回。业务记录应可查询、可导出，并能通过产物与业务系统状态核对结果；审计依据是这些记录，无需依赖模型内部思考过程。

当前原型：展示模板选择、岗位定制、项目关系与操作路径。后续实现：团队权限、可靠调度、版本关联、业务审计、案例评测与发布闭环。生成一份文档不等于业务任务已经完成。

07 / 验证路径

用业务结果，检验组织是否真正受益

先选择一条高频、输入输出相对清楚、有人负责验收的真实业务链，检验 BASE 能否在同等质量要求下减少总投入。以下是验证计划，尚无上线效果数据。

先记录基线，再比较变化

以“需求澄清 → PRD → 原型评审”为候选，记录原有方式的交付时间、返工原因和人工投入。试用后按相近复杂度比较，分别观察生成、等待、审核与维护，避免把熟练度提升误判成产品收益。

验证改进，也防止旧问题复发

从业务案例中整理正常任务、资料缺失、规则冲突与异常情境。改规则或换模型前，比较新旧方案在同一组案例上的结果；保留未参与修改的案例，检查改好一处是否影响其他任务。业务负责人校准判断标准。

对应价值重点观察
组织提效从需求进入到交付被接受的总周期、首次验收通过情况、等待与返工，以及同类问题是否反复发生。
岗位稳定新人独立完成任务所需时间、接手后的交付质量，以及长期使用中的修订与返工。
企业管理标准与资产是否有维护者，修改和发布是否有责任人，版本与验收记录能否追溯，投入能否关联业务结果。
个人提效完成任务的总投入：执行、审核、纠错、配置与分摊的维护成本，一并计入。

谁维护，谁拍板？

使用者反馈问题，领域建设者维护方法，业务负责人确定目标、验收标准与取舍，管理员负责权限和运行。人员接手时，材料、配置与维护责任一起交接。

何时升级，何时拆分？

资料与输出形式不同，先通过配置适配；目标、标准或权限长期冲突，再拆分模板。升级需要说明变化、验证效果，并保留现有实例的可用性与回退路径。

组织提效仍需要业务团队共同调整协作与责任。先让一类任务可靠交付，再验证经验能否被其他人持续复用；两者都有收益，才逐步扩展到更多业务流程。
